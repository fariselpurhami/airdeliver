# Complete opening identity contract, revision 1

Owner live evidence on main1d8574c: successful opening provider call consumed1000completion tokens at the1000cap, parsed the schema, then failed writer_identity. This proves the returned array did not match the expected complete active row identity set. It does not prove malformed truncated JSON: schema parsing had already passed. Missing rows, duplicate labels or changed labels could all satisfy the old permissive1..4free-label array schema.

The new request-specific OpeningBatch schema has one required object key for each active server-owned row label. Each value is a bounded introduction/insight draft. Missing/extra keys are invalid on both native strict-schema and local validation boundaries. Duplicate JSON keys are rejected explicitly rather than silently collapsed by the JSON parser. No fuzzy label matching, row reassignment or partial opening publication is allowed.

Both paragraph fields remain required single nonempty paragraphs. Per-row text is capped350characters per paragraph, claims capped10records, and the prompt asks at most40words total. All existing evidence, numeric, synthetic fixture and independent review gates remain. Every attached row card still reaches the model and reviewer; no catalog subset is selected to fit the output.

The four-row opening completion cap is1800, restoring output headroom rather than keeping the too-small1000cap. Provider finish_reason=length is rejected before content parsing, even if the text happens to be a syntactically valid partial object. This fails closed, not a repair burst. Shared Redis admission still applies to the higher reservation and may withhold generation when current quota is insufficient. No promise all opening+chat requests fit8000TPM or respond within seconds.

Actual tests cover active1/2/4row native required-key schemas, missing/extra/duplicate identities, length termination of valid JSON, all four rows and ten cards each, independent review rejection, evidence rejection, and PostgreSQL/Redis publication. No external provider or owner-machine execution. Live opening output is still required after rollout. Canonical55live acceptance remains unchanged. Granite activation and old models/indexes are untouched.

Owner console photo shows an8KTPM limit, roughly30RPM and an aggregate usage spike just below8K, with200responses in that window. The default shared rolling admission ceiling is now7200estimated/reconciled tokens, reserving nominal10% headroom. Reservations are still estimates, not exact Groq-tokenizer measurements. Compact JSON serialization reduces repeated whitespace in writer and reviewer payloads. API and worker generation is serialized/budgeted but not deduplicated by this patch, so a second opening can be withheld by the shared ledger. Such a withheld opening is not a successful UX acceptance result. A single page's cost cannot be read from the aggregate console plot.

# Payment cart cleanup bound to checkout snapshot

Canonical checkout stores its original cart snapshot alongside the existing frozen payment request. Successful PaymentCompletionService cleanup deletes only that same Redis snapshot through WATCH/MULTI. A newer cart survives. Old orders without a trustworthy snapshot preserve their cart, rather than guessing that it belongs to an old payment. This compatibility choice can leave already-paid items visible for legacy orders; paid order state and notifications still complete.

Combined migrated PostgreSQL19 and real disposable Redis tests cover unchanged cart deletion, newer cart preservation, legacy order preservation, and a repeated callback after a fresh cart is added. The two changed-cart cases fail against the previous unconditional delete; unchanged cleanup passes. Full local suite744 passed,3 skipped,20 existing warnings. No provider calls, gateway is controlled. Existing outbox tests remain passing. Not global cart revision/ABA protection, exactly-once payment, or DB/cache atomicity. If cleanup is unavailable after paid-state commit, cart preservation is safer; cleanup retry is still not durably journaled.

# Explicit capacity bounds

Literal hard features may now use explicit English at least/minimum/min or at most/maximum/max prefixes followed by an existing typed capacity token. The comparison requires the same RAM/memory, storage, SSD or HDD kind and the same normalized unit. Typed current SQL attribute evidence must satisfy the inequality. Plain exact capacity requirements remain exact, not silently upgraded. Ambiguous option strings fail closed. Bound matching does not use product-name extraction; the existing exact literal name behavior remains unchanged.

No MB/GB, GB/GiB or decimal/binary conversion is inferred. No localized comparator vocabulary or generic numbers are promoted. Unparseable recognized bounds fail closed rather than falling back to prose matching. This addresses narrow explicit bounds, not complete capacity/unit semantics.

Actual HTTP/PostgreSQL/Redis cases cover exact/min/max constraints with separately bound attributes, exclusion boundaries and publication. Direct cases cover wrong kind/unit, smaller/larger values, ambiguous options and missing evidence. Real-model extraction of the literal prefix remains unverified. No provider or owner-machine actions.

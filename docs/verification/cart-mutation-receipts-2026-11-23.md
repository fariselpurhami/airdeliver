# Atomic cart replay receipts, bounded Redis scope

Add/remove accepts an optional UUID mutation_id. HTTP accepts optional UUID Idempotency-Key, authenticated customer ID owns receipt namespace. Worker derives stable UUID from publisher message_id/routing key, preserved on broker redelivery; explicit payload IDs retained. Redis WATCH/MULTI commits cart snapshot and fingerprint receipt together. Same ID/body replays current cart hydration without a second mutation; changed body/operation conflicts. A competing same-ID transaction rechecks receipt. Receipt retention7days; cart24hours. Old callers without ID retain existing behavior. No schema migration in this checkpoint.

Real Redis tests cover committed-write/lost-response replay through a new service instance, same-ID/body conflict, customer isolation, competing same-ID commits, and delayed remove replay after re-add. HTTP validation/transport and stable broker ID tests are controlled. Full PostgreSQL19/Redis local suite815passed4skipped20existing warnings. Existing actual AMQP tests continue in CI, but these new replay cases are not broker-process-loss tests.

Important limitation: this is NOT durable exactly-once across Redis loss/eviction. Current Redis snapshot persistence and allkeys-lru can lose receipts. Expiry allows a later same ID to execute again. Redis Cluster cross-slot operation is not supported by these existing key shapes. Frontend still needs operation-key lifecycle wiring. Clear/save are not covered yet. A PostgreSQL operation journal, revisioned state and reconciliation remain required for durable replay semantics and are next. No deployment, provider calls, memory widening or Redis configuration change.
